# APR Agent Traceability Research

## Status

`EXPLORE` / supporting research only.

This document preserves SSSF-relevant findings from:

- **Understanding Automated Program Repair Agents Through the Lens of Traceability**
- arXiv: `2506.08311`
- current v2 reviewed because it materially extends the earlier v1.

The paper is a trace-analysis research source, not an authorization for a new trace database, observability daemon, or workflow taxonomy.

## Governing interpretation

SSSF should emit typed execution facts natively at the point of action and keep semantic interpretation separate and provenance-tagged.

> **Execution emits facts; analysis assigns meaning.**

Authoritative observations remain distinct from derived labels such as localization failure, reproduction failure, patch refinement, or likely loop behavior.

## EXPLORE-1 — Execution facts vs semantic trace interpretation

Owner-emitted trace/evidence records should bind exact identities and effects, including as applicable:

- inner-unit / parent / execution-cell / outer-attempt identity;
- action/tool identity and parameters;
- source/working generation;
- observed result/output;
- mutation/effect identity;
- VerificationContract result;
- timestamps/budgets;
- cleanup/terminal facts.

Semantic trajectory annotations are derived analysis and should carry their own provenance/evidence refs and observation class (`INFERRED`, etc.). They must not rewrite underlying execution facts.

Routing: shared trace/evidence spine, FUT-008 analytics, Wayfinder/progressive-disclosure projections.

## EXPLORE-2 — Small semantic-phase taxonomy

A compact non-authoritative phase vocabulary may support telemetry and replay analysis, for example:

- specification/fact discovery;
- localization;
- reproduction;
- implementation/mutation;
- deterministic verification;
- semantic review;
- authority/policy;
- cleanup/quiescence.

The taxonomy is for analysis and scorecards, not a mandatory workflow engine. DSH and bounded-agent executions may realize phases differently.

## EXPLORE-3 — Shift-left reproduction contract

For defect-repair work where reproduction is applicable:

```text
issue/specification
      ↓
localization sufficient for a meaningful reproducer
      ↓
candidate reproducer
      ↓
WATCHED RED against exact baseline
      ↓
qualified reproduction evidence
      ↓
repair
      ↓
reproducer passes on candidate
      ↓
independent applicable regression/VerificationContracts
```

A generated reproducer is not evidence-bearing merely because an agent wrote it. If the pre-fix failure cannot be demonstrated where required, the result is FAIL/CNO according to the applicable contract.

Reproduction is applicability-driven; not every engineering task has a meaningful pre-fix failing control.

Routing: VerificationContract design and defect-repair execution classes.

## EXPLORE-4 — Test selection vs acceptance-test applicability

Separate:

- **inner diagnostic tests** selected/generated by agents to reduce uncertainty; and
- **acceptance tests/validators** selected by deterministic VerificationContract applicability.

Running tests is not equivalent to running the right required tests. An implementation agent cannot remove or redefine its own acceptance obligations.

Routing: VerificationContract applicability and DSH refinement.

## EXPLORE-5 — Information-limited vs search-limited failure

Before increasing inference/sampling/refinement, classify whether the current failure is primarily:

- **information-limited:** missing/underspecified requirements, missing environment/context, unresolved fact dependency; or
- **search-limited:** sufficient information exists but the current candidate/search process has not found a valid solution.

More sampling should not be the default response to missing information. CODE-owned policy should prefer context/fact improvement or correct authority escalation when information is the bottleneck.

Routing: DSH-2, FUT-005, lowest-sufficient-autonomy policy.

## EXPLORE-6 — Patch-footprint telemetry

Record patch breadth for evaluation/review burden:

- changed lines/hunks;
- files touched/added/deleted;
- unexpected writes/scope expansion;
- comparison to historical baseline where useful.

Patch minimality is not a correctness oracle. Correct solutions may differ structurally from a historical/developer patch.

## EXPLORE-7 — Architecture/profile diversity for Best-of-N

Candidate diversity may arise from different solver architectures/profiles, not only stochastic resampling of one agent.

Future FUT-006 evaluation should compare heterogeneous qualified solver profiles against repeated-sample baselines and measure discovery/selection value, cost, latency and review burden.

## Additional supporting observations

- Localization, reproduction, implementation and validation failures should be measured separately in the harness scorecard.
- Localization context may improve generated reproducer quality; progressive context narrowing remains preferred.
- Preserve attempted evidence (failed reproducers, false localization hypotheses, irrelevant targeted tests) for replay/diagnostics without making failed workspace state canonical.
- Tool primitive and semantic operation are different levels of traceability; preserve both when useful.
- Traceability benefits do not require private chain-of-thought as an engineering artifact.
- Hybrid architectures combining structured narrowing with open-process exploration are strongly supported as a future DSH direction.

## Non-decisions

This research does **not** authorize:

- a second authoritative trace database;
- a trace-monitoring daemon as source of truth;
- mandatory reproduction tests for inapplicable work;
- semantic trace labels as deterministic fact;
- patch-size acceptance thresholds;
- immediate FUT-006/DSH state promotion.
